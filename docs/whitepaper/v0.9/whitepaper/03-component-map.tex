\section{A Component Map for a Changing Ecosystem}
\label{sec:component-map}

The component model supports a practical map of supplied roles and remaining integration work. A buyer can use it to locate a product in the architecture and identify the contracts still required. An implementer can use it to assemble a control plane from existing services and evaluate new tools as they appear.

Figure~\ref{fig:component-map} classifies components by \emph{responsibility} and \emph{privilege placement}. An unassigned required role exposes an ownership gap; a supplied role with a missing interface, uncovered path, or weaker target guarantee exposes a contract gap. Gap discovery follows from the declared action's requirements. One product can supply several roles, and several products can jointly supply one role.

\subsection{Nine Roles and Their Boundaries}

Table~\ref{tab:component-placement} summarizes the nine roles. The Agent Plane hosts existing agentic workflows; the Control Plane owns admission and execution authority; the Enforcement Plane mediates protected effects. Evidence Providers contribute observations and judgments across these boundaries rather than forming another privileged execution plane. Evidence acquisition scheduling is an optional strategy within admission, not an additional mandatory component.

\paragraph{Existing controllers and governance proposals.}
KedgeFlow also builds on work that directly addresses control. Microsoft's Agent Control Specification (ACS) specifies deterministic, fail-closed intervention-point verdicts and host obligations, including approval identity binding~\cite{acs2026}. Agent Infrastructure Control Protocol (AICP) proposes a lifecycle linking freshness-labelled situations, exact plans, approval, execution, verified outcomes, and recovery~\cite{aicp2026}. Proof-Carrying Agent Actions (PCAA) and Canonical Action Verification and Attestation (CAVA) describe portable action certificates, canonical action identity, approval binding, and receipts~\cite{pcaa2026,cava2026}; Fernandez's Agent Control Protocol (ACP) addresses stateful temporal admission~\cite{fernandezacp2026}. These drafts and working papers overlap individual KedgeFlow roles. Their publication does not establish conformance to the complete architecture, and this whitepaper does not report independent validation of their implementations. KedgeFlow's proposed contribution is the explicit composition of responsibilities and interfaces, not a claim to invent every underlying mechanism.

\subsection{Governed MCP Proxy Binding}
\label{sec:governed-mcp}

The \emph{Governed Reverse MCP Execution Gateway} is a deployment pattern for the Execution Gateway role, not a tenth component. An existing harness keeps its model, planner, graph, and ordinary tool integration. Its MCP endpoint resolves to a protected gateway; an Agent Adapter supplies the admission workflow and grant carriage. The gateway terminates client authentication, resolves tool identity against a trusted Resource Registry, and opens a separately authenticated upstream connection. The upstream mutation credentials are inaccessible to the Agent Plane, and direct upstream access to governed effects is blocked by the declared deployment boundary.

The binding pins MCP revision 2026-07-28 and the proposed \texttt{KF-MCP-0.1} profile. MCP request metadata includes the required protocol version and client capabilities; client identity metadata is self-reported and is not workload authentication~\cite{mcpbase2026}. Modern MCP negotiates extensions per request rather than through an initialization handshake~\cite{mcpversion2026}. The client declares the \texttt{io.kedgeflow/governed-mcp} extension in its capabilities' \texttt{extensions} map with \texttt{profile: KF-MCP-0.1}; the gateway advertises the same supported profile through discovery.

The proposed profile adds \texttt{-32001 NEEDS\_EVIDENCE}, a structured \texttt{RemediationContract}, and the HTTP \texttt{Mcp-KedgeFlow-Grant} header. A RemediationContract names missing evidence and the supported admission and retry path; it supplies no execution authority. A signed \emph{envelope} packages a typed payload with its schema, issuer-key reference, and signature metadata. The header contains unpadded base64url encoding of the complete signed \texttt{KF-JSON-0.2} grant envelope. These additions require documented discovery/configuration and explicit client support. A runtime without that support cannot be assumed to parse a custom error, obtain evidence, or attach a grant merely because it supports MCP.

Unsupported protected invocations fail closed; a deployed compatibility adapter may expose a standard MCP tool error with \texttt{isError=true}, but it must preserve the same proposal identity and admission semantics. Native MCP distinguishes protocol errors from recoverable tool execution errors~\cite{mcp2026}; the custom admission response is a profile decision, not a change to that distinction.

The governed invocation lifecycle is:
\begin{enumerate}
\item The gateway authenticates the caller and classifies the registered tool using its versioned Consequential Tool Descriptor (CTD). Unknown tools, changed input schemas, and undeclared invocation paths are rejected. Server-supplied annotations are not accepted as authority to downgrade consequences. A \texttt{ReadOnly} classification still requires access authorization: a read may disclose protected information, trigger a billable operation, or return hostile content. An authorized epistemic call may pass through with structured, redacted telemetry.
\item For a consequential \texttt{tools/call} without a redeemable grant, the gateway binds the registered tool identity and canonical arguments and returns a non-dispatching remediation response. The Agent Adapter freezes full proposal $q$ at admission; a pre-proposal response marks its proposal digest as null. A response for an existing proposal binds $H(q)$. The contract supplies unmet obligations, profile/carriage, an expiry, and an authenticated admission endpoint. The admission flow establishes the active policy epoch for the exact proposal. The error does not carry target credentials or authorizing authority. The adapter validates the endpoint against its configured trust domain rather than treating an arbitrary tool error URL as trusted.
\item The Agent Adapter gathers witnesses and invokes admission for that exact proposal. A valid certificate $C_q$ records discharged obligations; the Grant Authority issues $G$ under the root ledger. Changing arguments, target incarnation, schema, or a required policy binding requires fresh admission. The adapter resubmits the same logical operation with a new JSON-RPC request identifier and the profile's grant carriage. MCP request identifiers correlate transport exchanges; they are not execution idempotency keys.
\item The gateway verifies the proposal and grant bindings, subject/workload identity, proof-of-possession, expiry, policy epoch, and root generation. It atomically claims the allowance before opening target execution. It then obtains a narrowly scoped target credential through the configured exchange or federation service, invokes the Resource Adapter's declared guard, and records the resulting operation identity and outcome evidence. The header is consumed at the gateway, excluded from model-visible telemetry, and removed before upstream tool dispatch.
\item The Outcome Service distinguishes rejected admission, rejected guard, confirmed effect, and unresolved effect. A transport timeout after a possible dispatch yields \texttt{OUTCOME\_UNKNOWN}; the adapter retrieves the operation outcome instead of minting a new root or blindly retrying the mutation.
\end{enumerate}

The MCP-facing authorization token is audience-bound to the governed endpoint. MCP authorization prohibits accepting or passing through unrelated target tokens~\cite{mcpauth2026}. KedgeFlow therefore separates MCP server access from the target credential minted after a successful claim. The exchange service's policy maps the verified user delegation, workload identity, and $G$ to a target-specific credential. RFC~8693 specifies the OAuth token-exchange request; it does not make every AWS session, database token, or software-as-a-service (SaaS) credential a native token-exchange result. Each target needs an explicit supported binding, downscoping rule, lifetime, and enforcement contract~\cite{rfc8693,awssts2026}. Credential issuance and resource mutation are separate failure points, and neither enlarges the already claimed allowance.

\subsection{A2A Delegation Binding}
\label{sec:a2a-delegation}

A2A 1.0 supplies agent discovery and task transport; KedgeFlow supplies conserved execution authority. The proposed \texttt{urn:kedgeflow:a2a:root-reference:1.0} extension declares assurance requirements through \texttt{AgentCard.capabilities.extensions} and is activated using the binding's extension mechanism. For HTTP, the client sends \texttt{A2A-Version: 1.0} and the extension URI in \texttt{A2A-Extensions}. The public card at \texttt{/.well-known/agent-card.json} advertises the extension as required for governed skills; its \texttt{params.assuranceProfiles} lists the accepted profile identifiers. These are proposed KedgeFlow extension fields, not additions to the core A2A data model~\cite{a2a2026}.

The following is a complete structured Part example. A2A 1.0 uses the presence of \texttt{data} as the Part discriminator; it does not use the legacy \texttt{kind: data} field. The type URI below identifies the KedgeFlow payload schema, while \texttt{mediaType} identifies its serialization.

Here a \emph{Part} is an A2A message element carrying structured data. The root reference identifies ledger state to resolve through an authenticated authority endpoint; it does not authorize the receiving agent to execute.

{\small
\begin{verbatim}
{
  "mediaType": "application/json",
  "data": {
    "type": "urn:kedgeflow:root-reference:1.0",
    "root_id": "saga-drain-20261002-41",
    "root_generation": 7,
    "delegation_id": "delegation-drain-check-1",
    "assurance_profile": "cluster-maintenance-v1",
    "authority_endpoint": "https://control.example.org/kedgeflow/v1"
  }
}
\end{verbatim}
}

The Part contains a reference to authenticated ledger data, not a bearer grant, delegation token, or claim of control-plane ownership. The receiver's Agent Adapter authenticates to the configured authority endpoint, resolves the delegation descriptor, checks the intended workload/subject pair and the root generation, and obtains a child certificate for the precise delegated action. The Grant Authority performs \texttt{delegate(gid, childCertificate)} under the parent generation; it transfers or reserves child allowance in the same conserved ledger boundary before a child grant can be claimed. A task message cannot create a new allowance, enlarge the resource/action set, advance the root generation, or authorize further delegation beyond the parent's permissions.

This binding permits a planner, specialist, validator, or infrastructure agent to remain in its existing A2A workflow. The public AgentCard communicates what evidence and adapter guarantees the delegated skill requires; authenticated ledger resolution determines whether a particular child task has that authority. Capability advertising is not attestation of successful enforcement. A2A task and context identifiers are recorded alongside the execution root and operation identifier, but do not replace them. Every protected child effect follows the same Admission, Execution, and Outcome Interfaces; a completed A2A task is reconciled against the target receipts before its mutation is reported as confirmed.

\subsection{Policy and Saga Substrates}
\label{sec:policy-saga-substrates}

A Cedar integration treats policy evaluation as one deterministic stage of admission. The Policy Authority publishes a versioned policy/schema pair and separately defines the assurance obligations. The Admission Controller validates the request, entity graph, context types, and verified witness bindings before invoking Cedar; it records the input digest, determining policies, decision, and diagnostics. Cedar's \texttt{Allow} or \texttt{Deny} result does not natively collect witnesses or establish their provenance. An absent witness is represented as unmet evidence, not as an agent-supplied context boolean set to true. Because Cedar excludes a policy whose evaluation errors, the KedgeFlow admission wrapper rejects such diagnostics rather than allowing a failed safeguard to disappear from the admission decision~\cite{cedarauth2026,cedarvalidation2026}.

Temporal can persist the Outcome Service's reconciliation and compensation orchestration, while the Resource Registry describes each registered compensating action and the Grant Authority conserves its budget. This separation extends the original saga decomposition of a long-running transaction into local transactions with compensating transactions~\cite{sagas1987}. A compensation is a new governed effect with its own proposal, state guard, deadline, and receipt. It may be unavailable, only partially restorative, or invalid after another writer changes state. The service therefore registers compensation intent before the forward dispatch, reserves recovery allowance under the saga root, and runs only the compensations justified by known outcomes and their current guards~\cite{temporalsaga2023}. An unresolved timeout first enters reconciliation; it cannot justify blind retry or a presumed inverse. Compensation failure or insufficient reserved authority is an explicit recovery outcome, not a declaration that the workflow has rolled back.

\subsection{A Deployment Gap Register}
\label{sec:missing-pieces}

A gap is assessed against a \emph{named deployment, protected resource scope, threat model, and required guarantee}. The following status terms describe the implementation of each role, rather than the maturity of the whole industry:
\begin{itemize}
\item \textbf{Absent (missing):} no implementation is assigned to a required responsibility.
\item \textbf{Implicit:} behavior exists inside a hook, script, workflow, or service, but its owner, boundary, or callable contract is unspecified.
\item \textbf{Partial (incomplete):} an implementation covers only part of the required scope or lifecycle, or supplies weaker guarantees than the deployment requires.
\item \textbf{Unverified:} the capability is claimed, but documentation or test evidence does not establish the required behavior. Unverified is an evidence status and can accompany any claimed implementation; it is not evidence of absence.
\end{itemize}

A deployment records the applicable status, responsible implementation, protected scope, and test result for every row. Passing these checks establishes evidence for the tested scope and assumptions, not a universal safety guarantee. In particular, authority-ledger reservations cannot protect against actors outside the mediation boundary, and a gateway-signed receipt attests the gateway's report rather than necessarily a durable resource commit. The Resource Adapter and Outcome Service must distinguish a dispatch attempt, a confirmed result, and an uncertain effect using evidence the target actually supplies.

\subsection{Classifying the Next Tool}

Classify a new tool against a named action surface, not its marketing category:
\begin{enumerate}
\item Identify the supplied obligation, callable inputs/results, owned records and keys, and actual permission to affect the target.
\item Assign only those functions to the full component names. Record wrappers, trust enrollment, target prerequisites and interfaces still required.
\item Apply the gap statuses in Section~\ref{sec:missing-pieces}, and attach documentation or an executed test to every claimed contract. A passed case establishes verified evidence for that case's scope and assumptions; it is not a permanent product-wide status.
\end{enumerate}

For example, a hypothetical new policy checker returning a permit decision is an Admission Controller substrate. It is partial for that role until acceptable evidence, exact proposal/constraint binding and certificate issuance are implemented. If policy activation and revocation are handled only by an unowned script, the Policy Authority contract is implicit; if no grant issuer is assigned, the Grant Authority role is absent. Tests for the checker do not verify gateway custody or target guards. This procedure identifies required integration work without predicting a new class of product.

A deployment is complete when every required obligation has an explicit owner and verified contract evidence across the declared protected scope, irrespective of how many products supply its roles.
